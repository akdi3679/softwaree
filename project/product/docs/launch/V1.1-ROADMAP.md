# v1.1 Roadmap

> **Status:** Proposal. Not committed until engineering signs off.
> **Prerequisite:** v1.0 in production, at least 30 days of real usage.

Not a feature list. A decision record of what we said yes to, why, and
what we said no to.

---

## Yes

### 1. Wasmtime host wiring for the first two modules

**Why:** v1.0 has the IPC boundary but no dispatch. medical-reception
and food-lab are the two modules customers pay for.

**Deliverable:** both modules load, execute a command, produce an event.

**Estimate:** 3-5 days.

### 2. Real sync frame loop between Admin and User

**Why:** v1.0 wires the boundary. v1.1 makes it actually exchange events
over the wire.

**Deliverable:** a User connects to an Admin over LAN, receives 1000
events, and the projection matches the Admin's event stream.

**Estimate:** 3 days (after Wasmtime).

### 3. TOTP 2FA

**Why:** requested by the first 3 beta customers.

**Deliverable:** optional per-account TOTP, enforced at login.

**Estimate:** 1 day.

### 4. First-setup wizard end-to-end

**Why:** currently the wizard compiles but is not tested against a real
first-run.

**Deliverable:** a fresh install goes to a working project in < 15 min
without docs.

**Estimate:** 2 days.

### 5. Cloud-side read replica wiring

**Why:** Stage 2 of scaling path (SCALING-PATH.md). Read-heavy routes
should use the replica.

**Deliverable:** replica connection pool in use; write paths unchanged.

**Estimate:** 1 day.

---

## No

### A. Multi-tenant Cloud for a single Admin device

**Why not:** violates one-owner-per-datum (Principle 1). Any future
feature that wants this needs an ADR.

### B. Real-time collaboration on the Admin device

**Why not:** the model is single-writer. Real-time means multiple
writers, which means conflicts.

### C. Third-party module marketplace

**Why not:** the review and signing infrastructure is not there. v1.1
keeps modules as ours, licensed per project.

### D. Offline writes on the User app

**Why not:** ADR-009 is intentional. Revisit in v1.2.

### E. Full-text search across projects

**Why not:** cross-project queries violate the per-project isolation
model. Add per-project search (already exists) instead.

---

## Maybe (v1.2+)

- Additional modules: invoice, hotel, restaurant, gym, school (all
  skeleton in v1.0).
- iOS/Android read-only User app.
- Native Windows printing integration.
- Customer-hosted relay UI (currently manual setup).

---

## What we will measure

- Number of active modules per project (target: 1.2+).
- User app daily active (target: 40% of licensed users).
- Time-to-first-project (target: < 15 min).
- Support tickets per 100 projects (target: < 10/week).

If any of these is not moving 30 days after v1.1 ships, we stop and
analyze before building v1.2.
