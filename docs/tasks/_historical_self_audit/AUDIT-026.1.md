## OBJECTIVE
A test plan that covers all layers. Without it, "we shipped tested
software" is wishful thinking.

## WHY THIS WAS FOUND IN SELF-AUDIT
The spec has 1000+ tasks with simple `test -f` checks. That's
smoke tests, not a test plan. We need:
- Unit tests (per module, per function)
- Integration tests (across modules)
- E2E tests (full user flows)
- Security tests (pen-test, fuzzing)
- Performance tests (load, stress, soak)
- Chaos tests (failure scenarios)

## REQUIRED IMPLEMENTATION

Create `docs/architecture/TESTING.md`:

```markdown
# Testing Strategy

## Layers

### Layer 1: Unit tests (per function, per module)

**Where**: in the same file as the code (`#[cfg(test)]` in Rust, `.test.ts` in TS)
**Speed**: <1ms per test, all run in <30 seconds
**Coverage target**: 80% lines, 90% branches
**Who runs it**: developer on save, CI on every PR

### Layer 2: Integration tests (across modules within a service)

**Where**: `tests/` directory in each service
**Speed**: <100ms per test, all run in <5 minutes
**Coverage target**: every API endpoint has at least one happy + one error test
**Who runs it**: CI on every PR

Examples:
- Cloud: every endpoint has 2-3 tests (success, validation error, auth error)
- Admin: every command has 1 happy + 1 authz test
- User: every event application has 1 happy + 1 edge case
- Modules: every command has 3+ tests (happy, invalid input, authz)

### Layer 3: End-to-end tests (full user flows)

**Where**: `e2e/` directory in each repo
**Speed**: <10s per test, full suite <30 minutes
**Coverage target**: top 20 user flows
**Who runs it**: CI on every PR to main, before each release

Top flows to cover:
1. Sign up → create project → record first event
2. Invite user → user accepts → sees data
3. Run a module (medical-reception) → record a patient → see in User
4. Admin offline → User sees read-only state → Admin back → User can write
5. Backup → verify → restore (in sandbox)
6. Module install → configure → first use
7. Replace Admin device → new Admin takes over → all data preserved
8. GDPR export → user downloads → all data present
9. GDPR delete → all data gone within 30 days
10. Network drops during sync → reconnect → no data loss
11. Concurrent edits (User + Admin) → consistent state
12. Module uninstall → all data still queryable
13. Add 11th user to Clinic plan → add-on charged
14. Upgrade Starter → Clinic → all data preserved
15. Downgrade Clinic → Starter → data preserved, but plan-limited
16. Onboarding wizard → first project → first user
17. Sign in on new device → MFA flow
18. Recover from forgotten password
19. Multi-language: switch language, all UI translates
20. RTL: Arabic UI renders correctly

### Layer 4: Security tests

**Where**: security/ directory, run by security team
**Speed**: hours to days
**Who runs it**: before public launch, after major changes

Includes:
- **Pen-test** by 3rd party (Trail of Bits, Cure53, NCC, Bishop Fox)
- **Fuzzing** (cargo-fuzz for Rust, zod-fuzzer for TS)
- **SAST** (static analysis: CodeQL, Semgrep)
- **DAST** (dynamic: OWASP ZAP against Cloud)
- **Dependency scan** (cargo audit, pnpm audit, snyk)
- **Secret scan** (gitleaks, trufflehog)
- **Container scan** (trivy, snyk)
- **Crypto review** (any custom crypto is reviewed by 3rd party)

### Layer 5: Performance tests

**Where**: load-tests/ directory
**Speed**: hours (long-running)
**Who runs it**: nightly, before releases

Includes:
- Cloud: 10K concurrent users (k6)
- Cloud: 1M events/day (soak test)
- Admin: cold start <1s (Criterion)
- Admin: 1000 events/sec write throughput
- User: sync latency p99 <5s
- Module: 10K command invocations in <60s
- Search: 1M patients, FTS5 query <100ms

### Layer 6: Chaos tests

**Where**: chaos/ directory
**Speed**: minutes per test
**Who runs it**: weekly, before releases

Includes:
- Kill Admin mid-write
- Network partition Admin ↔ User for 1 hour
- Corrupt SQLite → recovery from backup
- Disk full → graceful failure
- Admin's clock skewed 5 min → warning shown
- Concurrent events → consistent state
- Mid-message WebSocket disconnect → reconnect
- Power loss mid-write → no data loss
- Malicious device tries to connect → rejected
- Cloud database failover → no data loss
- All our keys leaked → what happens (playbook)

## Test data

We need realistic test data:
- A clinic with 10K patients, 100K visits, 1M events
- A food lab with 5K samples, 50K test results
- Multi-language test data (Arabic names, Chinese, etc.)

Generated by fixtures, NOT real customer data (privacy).

## Test environments

- **dev**: local, fast feedback
- **ci**: shared, run on every PR
- **staging**: production-like, run before releases
- **prod**: monitored, chaos tests carefully scoped

## What we DON'T do

❌ Test in production only (must test before)
❌ Skip E2E "because unit tests are enough" (no, they catch different bugs)
❌ Real customer data in tests (privacy violation)
❌ Trust 100% coverage (mutation testing finds the real coverage)
❌ Skip flaky tests (flaky = broken)

## Tools

- Rust: cargo test, cargo-nextest, cargo-fuzz, criterion
- TS: vitest, playwright, k6
- DB: testcontainers (real Postgres, real MinIO in tests)
- Mock: only for external services (Stripe, email), never for our own code
- Coverage: cargo-llvm-cov, istanbul, codecov
- Mutation: cargo-mutants, stryker

## CI requirements

- Every PR: unit + integration + E2E + lint + type check
- Main: all of the above + security scan + load test smoke
- Tag: all of the above + full pen-test artifacts
- Weekly: full chaos + full load + mutation testing
```
