```markdown
# Disaster Recovery Runbook

## Recovery targets

| Metric | Target | How |
|--------|--------|-----|
| RPO (data loss tolerance) | 24h | Daily backup, last backup never more than 24h old |
| RTO (downtime tolerance) | 4h | Restore from backup + setup new Admin device |
| Backup retention | 30 days rolling | Cloud-side policy |
| Backup encryption | device_key + passphrase | AES-256-GCM |
| Verification | weekly | Automated via cron |

## Scenarios

### S1: Admin device hardware failure

**Detection**: Admin app won't start, disk error, etc.

**Recovery**:
1. Get a new device (laptop, same OS family)
2. Install Admin Tauri app
3. On first launch, choose "Restore from cloud backup"
4. Sign in with the same Account (the device key is regenerated)
5. Restore from the most recent backup, entering the original passphrase
6. Verify with: `Backup → Verify`
7. Re-invite any Users (their device keys are intact; they reconnect)

**Time**: 1-2 hours

### S2: Cloud data loss

**Detection**: Backup metadata endpoint returns 404 or 500.

**Recovery**:
1. Cloud is control-plane only; data is in Admin's SQLite
2. Restore Cloud from its own backup (see `docs/runbooks/CLOUD-DR.md`)
3. Existing Admin devices keep working — they only depend on Cloud for license + module delivery

**Time**: 2-4 hours for Cloud, 0 for Admin devices

### S3: Compromise of Admin device

**Detection**: Unusual activity in audit log, unexpected Cloud API calls.

**Recovery**:
1. Take Admin offline immediately (kill our mesh, power off)
2. From a fresh Admin device, log in to Cloud and **revoke the device**
3. Force a project rotate: any active Users must reconnect with new device keys
4. Restore from a backup taken BEFORE the suspected compromise
5. Run `Backup → Verify` to confirm integrity
6. Review audit log for any actions taken after compromise time
7. Re-issue any User invitations that may have been abused

**Time**: 2-3 hours

### S4: Project data corruption (e.g., a bad command corrupted the DB)

**Detection**: SQLite errors, missing rows, app crashes.

**Recovery**:
1. Stop the Admin
2. Restore from the most recent verified backup (Database → Backup → Restore)
3. The restore creates a new SQLite file and atomically swaps after 3 seconds
4. Open the project — verify counts
5. Replay any events that occurred since the backup (manual)

**Time**: 30 minutes

### S5: Network partition (Admin and Users can't reach each other)

**Detection**: Sync fails, Users see stale data.

**Recovery**:
- No data loss — Users can read cached data
- When network restored, Users automatically reconnect (auto-reconnect logic)
- If the partition lasted > 24h, Users may request a snapshot on reconnect

**Time**: 0 (no recovery needed, only patience)

## Backup testing

Every Sunday at 02:00 local time, the Admin runs:
1. `Backup → Verify` on the most recent backup
2. Records the result in the audit log
3. Alerts the Admin (notification) if any backup fails verification for 3 consecutive weeks

## What is NOT in this runbook

- Restoring from physical theft (see S3)
- Recovering the Cloud's own database (separate runbook)
- DR for an entire region going down (we self-host, single region is fine)

## Testing the runbook

Every 6 months, the team must:
1. Spin up a new Admin device
2. Restore a 30-day-old backup
3. Verify all projections render correctly
4. Time the restore
5. Update RTO estimate if it has changed
```
